# 项目上下文

最后核验：2026-08-13

本文只记录可跨会话复用的产品事实和约束。临时讨论、实现草案和单次故障证据不进入本文。

## 最终目标

### 已确认事实

- 仓库需要一套长期适用的 Agent 协作、架构决策、Phase 执行和验收机制，使新 Codex 会话能够低成本恢复上下文并自主完成普通开发阶段。
- 本轮只建设协作与交付基础设施，不开发具体业务功能。

### 当前假设

- 目录名“ESP32-S3开发”提示未来项目可能使用 ESP32-S3，但这不是已确认的产品或硬件需求。

### 尚未验证

- 最终产品解决的问题、目标用户和成功标准。
- 目标开发板、芯片变体、外设、电气连接和资源预算。
- SDK、语言、构建系统、运行环境和部署方式。

因此，当前不能诚实定义业务产品的最终目标。获得产品证据后应替换本段，而不是把猜测升级为约束。

## 当前明确需求

- 以仓库内文档保存当前产品目标、架构、长期决策和阶段状态。
- 以小而可验证、可回滚的 Phase 推进开发，并为正式 Phase 保存简短验收报告。
- 普通实现由 Codex 自主完成闭环；只有触及长期架构边界或缺失关键产品决定时才升级咨询。
- 以证据驱动测试和验收，以 Git 提交表示已通过验收的阶段基线。
- 减少无目的仓库遍历、重复历史读取和近似方案的反复试错。

## 非目标

- 本轮不选择硬件、SDK、框架、协议、数据模型或持久化方案。
- 本轮不创建示例业务代码、占位测试、空模块或推测性抽象。
- 本轮不把流程文档当作业务架构，也不为普通实现细节创建 ADR。

## 已确认约束

- 已验收代码默认视为稳定资产；优先增量演进，遵循 YAGNI。
- 需求、架构、测试证据和文档必须一致；证据不足时明确未知，不得猜测。
- 同一时间只推进一个未验收的正式 Phase。
- 不得通过删除测试、降低标准、隐藏异常或修改需求来绕过失败。
- 用户已有修改和无关文件必须保留，不得混入阶段提交。
- 凭据和敏感值不得进入仓库或提交历史。

## 暂时不做

- 在产品目标和硬件边界确认前，不建立业务路线图。
- 在出现第一个具有长期影响的技术选择前，不创建占位 ADR。
- 在存在可重复业务验收对象前，不引入 CI、覆盖率门槛或发布流水线。

## 维护规则

- 新证据进入时，将条目放入“已确认事实”“当前假设”或“尚未验证”之一。
- 假设只有在代码、测试、硬件实测、官方接口或用户明确决定支持后才能升级为事实。
- 已失效需求应删除或移入相关 ADR/阶段报告，不在本文累积时间线。
