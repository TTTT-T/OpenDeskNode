# Phase 交付与验收机制

本文定义正式开发阶段的最小闭环。具体阶段内容只写在 `docs/STATUS.md`，完成证据写入对应阶段报告。

## 1. Phase 启动

开始前检查 Git 工作区，并在 `docs/STATUS.md` 写明：

- 阶段编号和名称；
- 单一本阶段目标；
- 明确非目标；
- 预计修改模块；
- 可复现的验收标准；
- 风险、依赖和回滚点。

Phase 应范围清晰、可测试、可回滚。若同时包含大规模重构、新功能、框架迁移、性能优化或 UI 改版中的多个方向，先拆成可独立验收的子阶段。

## 2. 执行方式

正式 Phase 使用：

`Inspect → Plan → Implement → Test → Review → Report → Commit`

小改动无需形式化计划。Agent 自主决定可从现有证据推导的实现细节，并持续保留用户已有修改。实现只覆盖当前 Phase 的已确认需求，不为假想未来预建抽象。

## 3. 验收门槛

每个正式 Phase 结束前必须确认：

- 本阶段目标由明确输入/输出、自动测试、可重复命令、日志或可观测结果证明；
- 新增或修改测试覆盖本阶段行为，原有相关测试仍通过；
- 没有已知明显回归、无关改动或不必要复杂度；
- 没有临时调试代码、被吞掉的异常、被弱化或删除的测试；
- 架构、ADR、项目上下文和实际代码一致；
- 新发现的重要假设、限制和未解决问题已经记录；
- 回滚点仍明确可用。

无法执行的检查必须记录原因、替代证据和剩余风险。没有证据时状态保持进行中或阻塞，不得用“看起来可用”完成验收。

## 4. 失败处理

Bug 或验收失败按以下顺序处理：

1. 用最小输入稳定重现；
2. 获取相应时间窗的日志、测试、接口或硬件证据；
3. 定位根因并区分已确认原因与假设；
4. 添加能暴露问题的测试或可重复检查；
5. 实施最小修复；
6. 重跑原始重现路径和相关回归测试。

不得先随机调参、增加无依据等待、捕获并忽略异常或堆叠重试。Workaround 必须注明原因、影响和移除条件。

若针对同一核心问题连续两轮实质性修复仍失败，停止堆补丁，重新分析根因；若因此触及长期架构取舍，进入架构咨询。

## 5. 架构咨询包

只有触及 `AGENTS.md` 定义的升级边界时暂停。咨询内容按以下顺序组织：

### 背景

给出当前相关架构、本阶段目标和有效 ADR 链接。

### 当前问题

描述实际行为、期望行为和影响范围。

### 已确认事实

列出可复现步骤、日志、测试结果、硬件/API 行为和已核对的官方资料；把推测单列为假设。

### 已尝试方案

对每个方案说明改了什么、结果是什么、为什么停止或回滚。

### 候选方案

列出真正可行的 A/B/C 方案及长期代价，不为凑数制造候选项。

### Codex 当前倾向

明确推荐某一方案以及它最符合哪些已确认约束。

### 希望咨询的问题

只提出无法从仓库证据决定、会实质改变结果的最小问题。

咨询结论具有长期影响时先写 ADR，再恢复实现。

## 6. 阶段报告

正式 Phase 通过验收后，在 `docs/phase-reports/` 新增一份简短报告，文件名使用阶段编号和稳定主题。报告只包含：本阶段目标、实际完成、验收结果、主要测试、重要实现决定、已知限制、未解决问题和下一阶段建议。

报告引用命令和结果摘要，不复制大量 Git diff 或完整日志。随后将 `docs/STATUS.md` 更新为“无进行中 Phase”，并链接该报告。

## 7. Git 阶段控制

- 启动：检查分支和工作区；高风险操作先建立明确基线。
- 执行：允许按可审查单位创建小提交，禁止混入无关修改。
- 完成：只暂存本 Phase 文件，审查 staged diff，确认验收后创建代表完成态的提交。
- 提交信息：`<type>(phase-<id>): <result>`。
- 回滚：优先使用阶段开始前基线或独立提交进行可审查回退，禁止用破坏性命令覆盖用户工作。

## 8. 周期维护

至少每完成三个正式 Phase，或每次架构变更 Phase 完成时，检查：当前架构是否匹配代码、ADR 状态是否正确、`STATUS` 是否失真、文档是否重复冲突、workaround 是否达到移除条件。只修正真实漂移，不为维护动作扩张文档数量。
